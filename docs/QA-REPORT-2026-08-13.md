## 1. Executive Summary

The environment was brought up from a clean clone with **no database and no OAuth issuer
required**, exactly as `.env.example` advertises. The app builds, boots, authenticates, and
all 13 web routes render with seeded data. Automated quality gates are clean: **1,595 tests
pass, TypeScript reports 0 errors, ESLint reports 0 errors**.

Four new defects were found, all reproduced twice:

- **SP-073 (High)** — every screen in the app fires a request that returns **HTTP 500**. The
  in-memory dev database has no `recurringTransactions` table, so the Recurring module cannot
  be exercised at all in the environment the project documents for QA.
- **SP-074 (High)** — that 500 is **rendered as a normal empty state**. `/recurring` reports
  "0 rules — No recurring rules yet" while the backend is failing. A user cannot distinguish
  "my rules are gone" from "my rules never existed". This masking is production-relevant
  independent of SP-073's dev-DB trigger.
- **SP-075 (Medium)** — transaction amounts have **no upper bound** on the client or the
  server. The API accepted `99999999999.99`, which exceeds the `decimal(12,2)` column it is
  stored in. Once such a row exists it poisons the dashboard total, the month summary and the
  projection.
- **SP-076 (Low)** — the amount field accepts letters and symbols while typing; submit-time
  validation catches it, so this is a polish issue only.

The rest of what was tested behaved correctly, and the validation layer is genuinely good:
empty, zero and negative amounts were all rejected with clear, specific, accessible messages.
Layout held at three viewports in both colour schemes with no horizontal overflow.

**The headline for the team:** nothing here blocks the web build, but SP-073 means a whole
feature is invisible to QA, and SP-074 is the more dangerous of the two — the app currently
lies quietly when a query fails.

```bash
pnpm install                    # 10.6s, exit 0

# .env — only these matter for local QA; DATABASE_URL is deliberately UNSET,

PORT=3000
NODE_ENV=development
JWT_SECRET=<32+ chars>          # openssl rand -hex 32
CARD_ENCRYPTION_KEY=<32 bytes>  # openssl rand -hex 32
EXPO_PUBLIC_API_BASE_URL=http://localhost:3000   # web client cannot derive this

# two processes
NODE_ENV=development npx tsx server/_core/index.ts          # API   :3000
```

**Authenticating the browser.** `POST /api/dev/login` returns a JWT but does **not** set a
cookie. The web client reads its token from `localStorage` under the key `app_session_token`
(`constants/oauth.ts:129`), so a QA session authenticates by injecting it:

```js
localStorage.setItem("app_session_token", <token from /api/dev/login>)
```

## 9. Bugs Found

### SP-073 — `recurringTransactions.list` returns HTTP 500 on every screen

**Module/Page:** Recurring transactions · `server/_core/devDb.ts`
**Type:** Functional / API · **Severity:** High · **Priority:** P1 (for the QA environment)
**Reproducibility:** Always (reproduced 2×, browser and direct API)

**Environment:** `http://localhost:8081`, Chromium, 1440×900, user `dev_local_user`, build 1.0.0,
in-memory dev DB (`DATABASE_URL` unset).

**Steps to Reproduce**
1. Start the API and web client per §4.
2. Sign in and open any route (the query is prefetched app-wide).
3. Observe the network panel, or call the endpoint directly:
   `GET /api/trpc/recurringTransactions.list` with a Bearer token.

**Actual Result** — HTTP 500:
```
TypeError: Cannot read properties of undefined (reading 'filter')
    at applyWhere (server/_core/devDb.ts:338:15)
    at devQuery (server/_core/devDb.ts:548:9)
    at Object.getUserRecurringTransactions (server/db.ts:1102:26)
```

**Expected Result** — 200 with an array (empty is fine for a fresh dev user).

**Root cause [Verified].** `server/db.ts:1105` issues
`SELECT * FROM recurringTransactions WHERE userId = ?`, but `recurringTransactions` is not a
member of the dev DB's `TableName` union (`server/_core/devDb.ts:21-31`) and has no entry in
`store` (`:60-70`). `store[table]` is therefore `undefined`, and `applyWhere` calls `.filter`
on it. TypeScript cannot catch this because the table name is parsed out of a raw SQL string
at runtime.

**Scope — read this before triaging.** This is a **dev/in-memory-DB defect, not a production
one**: against real MySQL the table exists and the query would succeed. It is filed as High
because `.env.example` explicitly designates the unset-`DATABASE_URL` path as the supported
mode for "local work or QA", and in that mode an entire shipped module cannot be tested,
demoed, or regression-checked at all.

**Evidence:** `docs/qa-evidence/sp-073-recurring-500-empty-state.png`; server log in §9 above.

**Suggested Fix:** add `recurringTransactions: []` to `store` and `nextId`, and
`| "recurringTransactions"` to `TableName`, in `server/_core/devDb.ts`. Optionally make
`devQuery` throw a named "unknown table" error so the next missing table fails loudly instead
of as a `TypeError` deep in `applyWhere`.

### SP-074 — A failed query renders as a legitimate "no data" empty state

**Module/Page:** `app/recurring.tsx` (pattern likely wider — see note)
**Type:** UX / Data integrity · **Severity:** High · **Priority:** P1
**Reproducibility:** Always (reproduced 2×)

**Steps to Reproduce**
1. With SP-073 present (any failing `recurringTransactions.list`), open `/recurring`.

**Actual Result** — the header reads **"0 rules"** and the body reads **"No recurring rules
yet — Create a rule to automatically log regular income or expenses."** There is no error
banner, no retry affordance, and no toast. The screen is indistinguishable from a genuinely
empty account.

**Expected Result** — an error state that says loading failed, with a retry action. A user
who *has* recurring rules must never be told they have none.

**Root cause [Verified].** `ListEmptyComponent` (`app/recurring.tsx:221-236`) branches only on
`loadingRecurringTransactions`; there is no `isError` branch, so the error and empty cases
collapse into the same UI.

**Why this outlives SP-073.** SP-073 is only the trigger that exposed it. Any query failure —
dropped connection, expired session, server restart — produces the same false "you have
nothing" for a financial record. That is a trust problem in a money app, and it is
production-relevant.

**Evidence:** `docs/qa-evidence/sp-073-recurring-500-empty-state.png` (500 in the network
panel, empty state on screen, same moment).

**Suggested Fix:** add an error branch to `ListEmptyComponent` driven by the query's `isError`,
with a retry that calls `refetch()`. Audit the other list screens for the same
loading-or-empty-only pattern.

### SP-075 — Transaction amount has no upper bound; the API accepts values the column cannot hold

**Module/Page:** Add Transaction · `app/add-transaction.tsx`, `server/routers.ts`
**Type:** Validation / Data integrity · **Severity:** Medium · **Priority:** P2
**Reproducibility:** Always (reproduced 2× via API, 1× via UI)

**Steps to Reproduce (UI)**
1. Dashboard → **Add Expense**.
2. Amount `99999999999999999999`, category **Groceries**, **Save**.

**Steps to Reproduce (API)**
```bash
POST /api/trpc/transactions.create
{"json":{"categoryId":1,"type":"expense","amount":"99999999999.99","date":"..."}}
→ HTTP 200, rows 9 and 10 created
```

**Actual Result** — the transaction saves. The dashboard then reads
**"This Month −$100,000,000,000,000,000,000.00"**, and the same corrupted figure propagates to
the month summary, the expense total and the projection. Note the entered value also lost
precision on the way through (`…99999` displayed as `1e20`).

**Expected Result** — rejected, client and server, with a message naming the maximum.

**Root cause [Verified].** Client validation is `/^\d+(\.\d{1,2})?$/` plus `> 0`
(`app/add-transaction.tsx:186-193`); the server's `transactionSchema` is the same regex plus
`> 0` (`server/routers.ts:151-157`). Neither has a ceiling. The storage column is
`decimal("amount", { precision: 12, scale: 2 })` (`drizzle/schema.ts:126`), whose maximum is
**9,999,999,999.99** — so `99999999999.99` is already out of range and was still accepted with
HTTP 200. On real MySQL this is an out-of-range error in strict mode, or a silent clamp in
non-strict mode; the in-memory dev DB has no such check, which is why it stored cleanly here.
The same unbounded pattern applies to `positiveMoneySchema` (`server/routers.ts:176`), used by
loans and budgets — **[Inferred]**, not separately tested.

**Evidence:** `docs/qa-evidence/sp-075-unbounded-amount-dashboard.png`.

**Suggested Fix:** add a shared max to the money schema — e.g. refine
`Number(v) <= 9_999_999_999.99` — and mirror it client-side with a message such as "Amount must
be less than 10,000,000,000". Apply it to `positiveMoneySchema` too so loans, budgets and
repayments inherit the same bound.

### SP-076 — Amount field accepts letters and symbols while typing

**Module/Page:** Add Transaction · **Type:** UX/Validation · **Severity:** Low · **Priority:** P4
**Reproducibility:** Always (reproduced 2×)

**Steps to Reproduce:** open Add Transaction, type `abc!@#` into Amount.
**Actual Result:** the field holds `"abc!@#"`. No inline feedback until Save.
**Expected Result:** non-numeric characters are ignored on entry, as in most money inputs.

**Note:** submit-time validation *does* catch this ("Enter an amount like 12.50"), so no bad
data reaches the server. This is polish, not a data risk. On web, `inputMode="decimal"` is a
keyboard hint only and does not filter input.

**Evidence:** `docs/qa-evidence/sp-076-amount-negative-rejected.png` (shows the paired
rejection message for `-5`).

## 13. Risk Areas

1. **Error-state handling across list screens.** SP-074 is one confirmed instance of a pattern
   that likely repeats. This deserves a dedicated sweep before release.
2. **Money bounds across every financial schema.** SP-075 shows the ceiling is missing where
   the floor is enforced; loans, budgets and repayments share the schema.
3. **The dev-DB / MySQL divergence itself.** SP-073 exists because the two paths drifted. Any
   table added to `drizzle/schema.ts` without a matching `devDb` entry fails the same way, at
   runtime, invisibly to the type checker.
4. **Everything in §12** — the untested majority of CRUD is the largest unknown in this report.

## 14. Recommendations

**Before release**
1. Fix SP-074 (error branch on list screens) — the highest-value fix here.
2. Add a maximum to the shared money schema (SP-075), server first.
3. Fix SP-073 so Recurring is testable in the documented QA environment.

**Engineering**
4. Make `devQuery` throw a named error for unknown tables so drift fails loudly.
5. Consider a test asserting every table in `drizzle/schema.ts` exists in `devDb`'s `store` —
   this class of bug would then be caught in CI, not by QA.

**QA process**
6. Run a full regression against SP-001…SP-072 — this session did not.
7. Get a device or simulator into the loop; a meaningful share of this app (app lock,
   biometrics, notifications) has never been runtime-tested.

## 15. Final QA Status

🟡 **Passed with Minor Issues** — for the tested web scope only.

No crash, no data loss, no broken authentication, and the core money-entry path works
correctly with good validation. The two High findings are narrow: one is confined to the dev
database, the other is a missing error branch. Both are small, well-localised fixes.

This status covers **only** what §6 marks tested. Given how much of the CRUD surface is
Untested and that SP-001…SP-072 were not retested, **this report is not sufficient on its own
to certify a release.**
