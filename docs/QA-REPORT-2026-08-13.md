## 1. Executive Summary

### 1.1 Understanding of the project

SmartPocket is a cross-platform personal-finance manager built from a single Expo/React Native
codebase targeting iOS, Android and web. Its stated purpose (`docs/concept note.md`) is to give
everyday users a free, privacy-conscious tool that unifies four things competitors usually
split apart: **day-to-day income/expense tracking**, **budgeting**, **personal loan management**,
and **AI-assisted insight**.

The delivered surface is broad for a 1.0: transactions with categories, multi-account support,
credit cards, category budgets, recurring-transaction rules, loans with repayment schedules,
CSV import, CSV/JSON export, a seven-currency setting, three colour themes with light/dark
modes, month-over-month trend charts, and a month-end spend forecast.

An important framing note: `docs/concept note.md` describes an _offline-first, local-storage_
product, but the app as built is **server-backed** (Express + tRPC + Drizzle/MySQL) with all
data held server-side per user. The concept note carries a correction banner acknowledging
this. The gap matters because "privacy-conscious, data never leaves your device" is the
product's headline differentiator and is **not** what the current architecture delivers.

### 1.2 Overall product quality assessment

**The engineering foundations are strong. The feature assembly is not finished, and the app's
error handling is its weakest layer.**

What is genuinely good, and should be said plainly:

- **Automated quality gates are clean.** 1,595 tests pass, TypeScript reports 0 errors, ESLint
  reports 0 errors. Very few projects at this stage hold that line.
- **Form validation is thoughtful.** Empty, zero and negative amounts are each rejected with a
  _specific_ message, and errors are wired to `accessibilityLiveRegion` with an explicit iOS
  announcement.
- **Submit buttons are correctly disabled until a form is valid** — a deliberate, consistently
  applied pattern across five of six forms.
- **Keyboard support works.** Tab order is logical and every focused control shows a visible
  2px outline.
- **Layout is solid.** 18/18 viewport × colour-scheme combinations rendered with no horizontal
  overflow.
- **Core money flows are correct.** Create, delete, search, filter, currency switching, theme
  switching, CSV/JSON export and browser back/forward all behaved correctly under test.

What is not finished:

- **Two entire modules — Recurring and Budgets — are non-functional** in the environment the
  project itself documents for QA. Both fail with HTTP 500 from the in-memory dev database.
- **Failures are invisible to users.** Budget creation fails with _no message whatsoever_, and
  the Recurring screen renders a backend failure as a friendly "you have no rules yet". In a
  money app, silently showing "nothing here" when the truth is "we could not load your data"
  is the most serious behavioural finding in this report.
- **Money amounts have no upper bound**, on either the client or the server, and the API
  accepts values the storage column cannot hold.

## 2. Testing Scope

### 2.1 Environment

Everything below runs with **no MySQL and no OAuth issuer**. Leaving `DATABASE_URL` unset
selects the seeded in-memory dev database (`server/_core/devDb.ts`), which `.env.example`
explicitly designates as the supported mode for "local work or QA".

```bash
pnpm install                                              # 10.6s, exit 0
NODE_ENV=development npx tsx server/_core/index.ts        # API   :3000
EXPO_OFFLINE=1 npx expo start --web --port 8081           # Metro :8081
```

Browser authentication needs one non-obvious step: `POST /api/dev/login` returns a JWT but sets
**no cookie**. The web client reads its token from `localStorage` under `app_session_token`
(`constants/oauth.ts:129`):

```js
localStorage.setItem("app_session_token", <token from /api/dev/login>)
```

## 11. Security Observations

Only passive, non-destructive observation was performed. No exploitation, injection, brute
force or unauthorised-access testing was attempted.

| Area                         | Finding                                                                                                                                                                                                                                                                                                                                             |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Server-side validation**   | ✅ Validation is **not** client-only. `transactionSchema` and `positiveMoneySchema` (`server/routers.ts`) re-validate every money field with Zod. Confirmed by direct API calls bypassing the UI. **[Verified]**                                                                                                                                    |
| **Missing validation bound** | ⚠️ The server accepted `99999999999.99`, exceeding its own `decimal(12,2)` column (SP-075). A data-integrity gap rather than a breach. **[Verified]**                                                                                                                                                                                               |
| **Authentication**           | ✅ tRPC endpoints require a Bearer token; `/api/auth/me` returns the correct user. The dev-login route is registered **only** when `NODE_ENV !== production` (`server/_core/index.ts:133`). **[Verified]**                                                                                                                                          |
| **Sensitive data exposure**  | ✅ Card numbers are masked everywhere in the UI (`•••• •••• •••• 1234`), and the schema encrypts them at rest via `CARD_ENCRYPTION_KEY`. No full PAN was rendered. **[Verified]**                                                                                                                                                                   |
| **Session token storage**    | ⚠️ On web the JWT is stored in `localStorage`, which is readable by any JS on the page and therefore XSS-exposed. The code documents this trade-off and recommends an httpOnly cookie for production (`lib/_core/auth.ts:20-25`). Acceptable for dev; **must be revisited before a production web release.** **[Verified — by source, documented]** |

## 14. Recommendations

### Must fix before release (P1)

1. **Surface mutation failures everywhere (SP-077, SP-074).** No user action should ever fail
   silently. Budget creation currently fails with zero feedback, and the Recurring screen
   reports a backend failure as "you have no rules". Adopt one shared pattern: on error, show a
   specific toast _and_ an inline error state with a retry. This is the highest-value fix in
   this report — it is small, and it fixes a class of bug rather than an instance.
2. **Fix the dev-database drift (SP-073, SP-077).** Add the missing `recurringTransactions`
   table, and teach the dev SQL parser the parenthesised OR predicate. Then add a test asserting
   every table in `drizzle/schema.ts` exists in `devDb`'s `store`, and make `devQuery` throw a
   named error for unknown tables — so this class of drift fails in CI rather than in QA.
3. **Bound every money field (SP-075).** Add a maximum to `positiveMoneySchema` and
   `transactionSchema` server-side, mirror it client-side, and confirm it against the
   `decimal(12,2)` column limit.

### Should fix before release (P2)

4. **Fix nested interactive elements (SP-078)** — invalid HTML causing hydration errors on two
   screens.
5. **Add accessible names to the 7 unlabelled inputs (SP-081)** and the empty Settings switch.
6. **Set `aria-checked` on radio controls (SP-080)** and **add per-route titles (SP-079)**.
7. **Add per-field inline errors to the New Card form** — a disabled button across six fields
   gives the user no way to know what is wrong.

### UX / product

8. Add a date picker to Add Transaction; add transaction edit; add recovery actions to the
   OAuth-failure and loan-not-found screens; document the CSV import format on the import screen.
9. Reconsider the desktop master/detail split, which leaves half the viewport empty.
10. Hide the AI toggle until an AI capability ships, and gate Theme Lab out of production.
11. Reconcile the "local-first / data never leaves your device" positioning with the
    server-backed architecture before any user-facing marketing.

### Security / maintainability

12. Move the web session token from `localStorage` to an httpOnly cookie before a production web
    release (already flagged in the code).
13. Suppress stack traces in non-development responses.
14. Keep the automated gates as they are — 1,595 passing tests with a clean `tsc` and ESLint is
    a real asset; extend them to cover the dev-DB/schema parity check in recommendation 2.

### QA process

15. **Run a full regression against SP-001…SP-072** — this session did not.
16. **Get a device or simulator into the loop.** App lock, biometrics, notifications and native
    alerts have never been runtime-tested.
17. **Test against real MySQL at least once per release** — two of the three High findings here

## 🟠 Requires Major Fixes Before Release _(as audited 2026-08-13 — superseded, see above)_

**Justification, from the evidence in this audit:**

- **Two of the product's four stated pillars are non-functional.** Budgets cannot create a
  single budget (SP-077, reproduced twice, HTTP 500) and Recurring cannot load at all (SP-073,
  reproduced twice, HTTP 500 on every screen in the app).
- **The failure-communication layer is unreliable.** Budget creation fails with _no message
  whatsoever_ — verified by polling the DOM for 8 seconds after submit — while a comparable
  category failure does toast correctly. The inconsistency means users cannot trust that the
  absence of an error means success. SP-074 is worse: it reports a backend failure as a factual
  claim about the user's data ("No recurring rules yet"). In a financial application this is the
  most serious behavioural finding in this report.
- **A data-integrity gap remains open.** Money amounts are unbounded and the API accepts values
  its own storage column cannot hold (SP-075), with a demonstrated ability to corrupt the
  dashboard, month summary and forecast.

**Why not 🔴 Not Ready for Production:** there is no crash, no data loss, no authentication
failure and no security breach. The core money-tracking path — the thing users will do daily —
works correctly and persists reliably, and the automated quality gates are clean.

**Why not 🟡 Ready After Minor Fixes:** SP-073, SP-074 and SP-077 are not cosmetic. They
disable advertised modules and break the app's ability to tell users the truth about their data.

**Important qualification.** SP-073 and SP-077 are **dev-database defects**. Against real MySQL
these queries would likely succeed, and the release picture would improve materially. But
(a) the affected environment is the one this project documents for QA, so both modules are
currently unverifiable, and (b) **SP-074's error-masking and SP-077's silent failure are
production-relevant regardless of the trigger** — any query failure in production produces the
same silence today. **A verification run against real MySQL is strongly recommended and could
change this recommendation.**
